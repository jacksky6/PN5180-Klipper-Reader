# PN5180 设计逻辑说明

本文档记录第一版 PN5180 Klipper 插件的设计取舍和内部流程，方便后续继续扩展。

## 设计目标

第一版只解决一个核心问题：

```text
通过 PN5180 读取耗材标签中的 spool_id，并可选交给 HappyHare 进行多色耗材映射。
```

所以实现范围刻意收窄：

- 优先支持硬件 SPI。
- 使用固定命令延时，减少接线数量。
- 支持 ISO14443A / NTAG 和 ISO15693 / ICODE SLIX2 读取。
- 复用 PN532 插件的上层行为：定时读取、重复卡防抖、解析 JSON、可选派发 `MMU_GATE_MAP`。
- 不处理写卡、加密卡、需要认证的私有标签和 Bambu Mifare Classic。

## 固定命令延时

第一版使用 Klipper 硬件 SPI 的 `cs_pin` 控制 NSS。曾尝试用主机层 `set_digital()` 手动控制 NSS，但这种方式会在 SPI 事务前后排入密集 MCU 定时事件，可能触发 `Timer too close`，因此不作为默认方案。

参考 `pypn5180` 的做法，插件在每条 PN5180 host command 后使用固定 `command_delay`，默认 5ms。接线必须包含 SPI 四线、CS、供电、GND 和 MCU 可控的 RST。RST 不再允许只硬件拉高，因为长时间运行后的 PN5180 卡死往往无法通过 SPI 软件命令恢复。

SPI 总线配置优先使用硬件 SPI：

```ini
spi_mcu: mmu
spi_bus: spi2_PB14_PB15_PB13
cs_pin: mmu:PA8
```

如果用户固件没有可用的硬件 SPI bus 名称，可以使用 Klipper 软件 SPI 显式指定这组丝印引脚：

```ini
spi_mcu: mmu
spi_software_sclk_pin: mmu:PB13
spi_software_miso_pin: mmu:PB14
spi_software_mosi_pin: mmu:PB15
cs_pin: mmu:PA8
```

## 命令延时和 IRQ 轮询的分工

固定 `command_delay` 解决的是 PN5180 host command 处理时间，不直接表示标签是否已经响应。

标签读取仍然需要轮询 PN5180 的寄存器：

- `IRQ_STATUS`：判断是否收到 RF 响应。
- `RX_STATUS`：判断接收缓冲区里有多少字节。
- `READ_DATA`：读取 RF 接收缓冲区。

因此仍然保留类似 RC522 的“寄存器轮询完成位”的方式。

## 插件结构

`pn5180.py` 分为四层：

| 类 | 职责 |
| --- | --- |
| `PN5180Handler` | PN5180 底层 SPI、固定命令延时、寄存器、RF、NTAG 读页、ISO15693 读块 |
| `PN5180Manager` | 标签读取流程、数据解析、spool ID 派发、防重复读取 |
| `PN5180Service` | Klipper reactor 定时任务 |
| `PN5180` | Klipper 配置入口和 G-code 命令 |

## 初始化流程

初始化大致流程：

```text
执行硬件复位：RST 低 100ms，高后等待 200ms
读取 PN5180 firmware EEPROM
RF_OFF
SYSTEM_CONFIG[2:0] 清零，使状态机回到 Idle/StopCom
清空 IRQ_STATUS
加载 ISO14443A RF 配置：loadRFConfig(0x00, 0x80)
打开 RF 场
SYSTEM_CONFIG[2:0] 置为 Transceive
等待 RF 稳定
```

`reset_pin` 是必填项。插件不再提供软件恢复兜底；所有初始化和恢复都通过硬件 RST 完成。这样把“需要断电重上电”的故障尽量收敛为 Klipper 可控的复位动作。

PN5180 读完标签或读卡失败后，内部状态可能停在 Receive/Transceive。为了避免隔夜或多次失败后不再寻卡，插件在每次寻卡前都会重新执行完整 RF 状态恢复，并按当前协议加载对应 RF 配置：

```text
RF_OFF -> Idle/StopCom -> clear IRQ -> loadRFConfig -> RF_ON -> Transceive
```

`PN5180 NAME=<name> RECOVER=1` 会执行一次硬件 RST，并重新初始化 PN5180。

如果 PN5180 长时间轮询后 SPI 读回 EEPROM 和寄存器全 `00` 或全 `FF`，说明芯片可能已经不再正常响应 host command。插件会按 `comm_check_interval` 在连续无卡扫描后做通信检查；发现异常时自动执行硬件 RST 并重新初始化。看门狗因此仍然保留，但它的职责是触发硬复位恢复，而不是依赖软件恢复命令。

## 寻卡流程

插件支持三种协议模式：

- `tag_protocol: auto`：先尝试 ISO14443A / NTAG，再尝试 ISO15693。
- `tag_protocol: ntag`：只尝试 ISO14443A / NTAG。
- `tag_protocol: iso15693`：只尝试 ISO15693。

自动识别不是靠一次 PN5180 通用命令判断“所有卡类型”，而是依次切换 RF 配置并执行对应协议的寻卡命令。这样接近 PN5180 参考项目的使用方式，也便于在调试时强制某一种协议。

ISO14443A / NTAG 寻卡基于 Spoolsense PN5180 Type A 逻辑移植：

```text
执行完整 RF 状态恢复并加载 Type A RF 配置
关闭 Crypto1
关闭 RX/TX CRC
发送 WUPA 或 REQA
读取 ATQA
发送 Cascade Level 1 anticollision
读取 UID + BCC
打开 RX/TX CRC
发送 SELECT CL1
读取 SAK
如果 UID 是 7 字节，继续 Cascade Level 2
```

NTAG 常见 UID 为 7 字节；如果标签返回 4 字节 UID，也会按实际 UID 保存。

ISO15693 / ICODE SLIX2 寻卡流程：

```text
执行完整 RF 状态恢复
加载 ISO15693 RF 配置：loadRFConfig(0x0D, 0x8D)
RF_ON
SYSTEM_CONFIG[2:0] 置为 Transceive
发送 one-slot inventory：flags=0x26, command=0x01, AFI=0x00
读取响应中的 DSFID 和 8 字节 UID
```

## 读取流程

NTAG 的 `READ` 命令是：

```text
0x30, page
```

一次返回 16 字节，也就是 4 个 page。插件从 NTAG 用户区 page 4 开始读取，并保留内部最大保护上限：

```text
64 pages / 4 pages per read = 16 次 NTAG READ
```

每次 READ 的流程：

```text
SEND_DATA: 0x30,page
轮询 IRQ_STATUS 等 RX_IRQ
读取 RX_STATUS，确认收到 16 字节
READ_DATA 读回 16 字节
```

读取过程中会检查 TLV/NDEF 长度和结束符。读到完整 NDEF 后立即停止。如果标签不是 NDEF/TLV 格式，则遇到全 `00` 空页数据时提前停止，内部上限只作为异常保护。

ISO15693 可以使用单块读取：

```text
flags=0x02, command=0x20, block
```

插件从 block 0 开始读取，并保留内部最大保护上限。ICODE SLIX2 常见 NDEF 数据前 4 字节是 Capability Container，例如 `E1 40 28 01`，真正 TLV 从 offset 4 开始。插件会识别这个结构，读到完整 NDEF 后立即停止；如果不是 NDEF/TLV 格式，则遇到全 `00` 空 block 时提前停止。

配置项 `iso15693_blocks_per_read` 控制每条读取命令读取多少个 ISO15693 block，默认值是 `8`。当该值大于 `1` 时，插件使用 `READ MULTIPLE BLOCKS`。批量读采用 addressed 模式：

```text
flags=0x22, command=0x23, UID(LSB first), start_block, block_count-1
```

profile 中的 `read_mode`、`batch_size`、`reads` 和 `blocks` 用来确认实际读取路径。读取策略只通过配置项调整，G-code 不提供临时覆盖入口，避免最终用户配置和运行时状态不一致。

## 数据解析流程

读取到用户区后，NTAG 和 ISO15693 共用同一套解析流程：

```text
按 UTF-8 解码
去掉末尾空字节
如果前面有 NDEF 头，寻找第一个 {
如果末尾有 NDEF 填充，截断到最后一个 }
优先按 JSON 解析
递归查找 spool_id / spool / filament 字段
JSON 失败后使用文本正则提取
```

如果 `happyhare_enable` 为 `True`，找到 spool ID 后执行：

```gcode
MMU_GATE_MAP NEXT_SPOOLID=<ID>
```

如果 `happyhare_enable` 为 `False`，插件只记录和显示 spool ID，不调用 HappyHare 命令。这样可以在没有 HappyHare 的调试环境中单独验证 PN5180 和标签解析。

## 防重复读取

插件读取成功后会保存当前 UID，并进入等待移除状态。

在标签未移除前：

- 相同 UID 不会再次完整读取。
- 启用 HappyHare 派发时，不会重复派发 `MMU_GATE_MAP`。
- 检测到标签移除后，读卡器重新进入 ready 状态。

## 后续扩展方向

后续可以按这个顺序扩展：

1. 增加写 NTAG page / ISO15693 block 的命令。
2. 增加 OpenSpool / OpenTag3D / Bambu 标签格式解析。
3. 增加 OpenPrintTag 二进制格式解析。
4. 增加更细的错误统计和恢复策略。

第一版的重点是保持链路短、可调、方便实机验证。
