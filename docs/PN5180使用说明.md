# PN5180 Klipper 插件使用说明

本文档说明第一版 PN5180 插件的接线、配置和 G-code 用法。第一版目标是通过 SPI 读取 ISO14443A / NTAG 标签中的耗材信息，并把标签里的 `spool_id` 发送给 HappyHare。

## 功能范围

- 支持 PN5180 通过硬件 SPI 通信。
- 使用固定命令延时，减少接线数量。
- 支持读取 NTAG 用户区，默认读取 page 4 到 page 67。
- 支持从 JSON 或普通文本中提取 `spool_id`、`spool`、`filament` 字段。
- 读取到 spool ID 后自动执行：

```gcode
MMU_GATE_MAP NEXT_SPOOLID=<ID>
```

第一版暂不包含写卡、ISO15693、Bambu Mifare Classic 鉴权。

## 示例接线

以你当前 MMU 主板的 SPI 接口为例：

| PN5180 引脚 | MMU 主板引脚 |
| --- | --- |
| SCK | PB13 |
| MISO | PB14 |
| MOSI | PB15 |
| NSS | PA8 |
| RST | 推荐接 MCU GPIO；无 GPIO 时接可靠 3.3V |
| 5V / 3.3V | 本项目测试的 PN5180 模块需要同时接 5V 和 3.3V |
| GND | G |

`RST` 必须是高电平芯片才会正常运行。推荐把 RST 接到 MCU GPIO 并配置 `reset_pin`，插件会在初始化前执行一次低高复位。如果没有多余 GPIO，至少要把 RST 稳定拉到 3.3V，可以直接接 3.3V，也可以用 10k 上拉到 3.3V。

第一版使用 Klipper 硬件 SPI 的 `cs_pin` 控制 NSS。不要把 `cs_pin` 设成 `None` 再用插件手动拉 NSS；Klipper 主机层手动 GPIO 夹在 SPI 事务之间容易造成 MCU 定时队列过近，触发 `Timer too close`。

插件会像 `pypn5180` 一样在每条 PN5180 命令后使用固定延时。IRQ、GPIO、AUX、REQ 暂时都不接。

本项目测试的 PN5180 模块需要同时接 `5V` 和 `3.3V`：`5V` 供给模块射频/功放部分，`3.3V` 供给逻辑电源和 SPI 电平参考。只接其中一路可能导致 PN5180 不启动或 SPI 读回全 `FF`。如果诊断结果全 `0xFFFFFFFF`，优先确认两路电源、GND、RST 高电平、CS/MISO/MOSI/SCK 是否都正常。

## 安装

将插件文件放入 Klipper：

```text
klippy/extras/pn5180.py
```

重启 Klipper 后，在 `printer.cfg` 或 MMU 相关配置中加入下面配置。

## 配置示例

```ini
[pn5180 mmu_reader]
spi_mcu: mmu
spi_bus: spi2_PB14_PB15_PB13
cs_pin: mmu:PA8

# 推荐：如果 RST 接到了 MCU GPIO，则启用
# reset_pin: mmu:PC7

spi_speed: 100000
scan_period: 3.0
debug_log: True

# 默认读取 NTAG page 4-67，共 256 字节
start_page: 4
end_page: 67

# 时序参数，先用保守值跑通
command_delay: 0.005
rf_timeout: 0.05
rf_poll_interval: 0.001
rf_on_delay: 0.05
page_read_retries: 2
```

上面的 `spi_bus: spi2_PB14_PB15_PB13` 使用 MCU 固件中已经定义好的硬件 SPI 总线。以你提供的 STM32G0 枚举为准，这个总线名对应：

```text
spi_bus: spi2_PB14_PB15_PB13
BUS_PINS = PB14,PB15,PB13
MISO = PB14
MOSI = PB15
SCK  = PB13
NSS  = PA8，由 cs_pin 控制
```

`spi_bus` 不是插件自己定义的名字，而是 Klipper MCU 固件支持的硬件 SPI 总线名称。不同 MCU 或不同固件配置可能不一样。如果用户的固件里没有可用的硬件 SPI 总线名，或者不确定 `spi2_PB14_PB15_PB13` 是否可用，可以先用软件 SPI 显式指定引脚：

```ini
[pn5180 mmu_reader]
spi_mcu: mmu
spi_software_sclk_pin: mmu:PB13
spi_software_miso_pin: mmu:PB14
spi_software_mosi_pin: mmu:PB15
cs_pin: mmu:PA8

spi_speed: 100000
scan_period: 3.0
start_page: 4
end_page: 67
```

硬件 SPI 优先，软件 SPI 主要用于总线名不可用或移植到其他板子时排查问题。

如果你的 RC522 已经使用同一个 SPI 接口，测试 PN5180 时不要同时启用 RC522 插件，避免两个设备同时占用同一组 SPI 和 CS。

## G-code 命令

启动后台读取：

```gcode
PN5180 NAME=mmu_reader READ=1
```

停止后台读取：

```gcode
PN5180 NAME=mmu_reader READ=0
```

单次扫描：

```gcode
PN5180 NAME=mmu_reader SCAN=1
```

重新初始化：

```gcode
PN5180 NAME=mmu_reader INIT=1
```

手动恢复 PN5180 RF 状态：

```gcode
PN5180 NAME=mmu_reader RECOVER=1
```

查看状态：

```gcode
PN5180 NAME=mmu_reader STATUS=1
```

`STATUS=1` 会显示是否正在后台读取、扫描次数、上次扫描结果、上次 UID、上次 spool ID、最近事件和最后错误。

调试输出开关：

```gcode
PN5180 NAME=mmu_reader DEBUG=1
PN5180 NAME=mmu_reader DEBUG=0
```

`debug_log: True` 或 `DEBUG=1` 时，每次后台扫描都会输出一行，例如无卡、等待移除、读到 UID、解析 spool ID、错误原因等。调试阶段建议打开；稳定后如果嫌 Web console 太吵，可以设为 `False` 或执行 `DEBUG=0`。

读取底层诊断寄存器：

```gcode
PN5180 NAME=mmu_reader DIAG=1
```

如果诊断结果大量出现 `0xFFFFFFFF` 或 firmware raw 为 `FF FF`，说明 PN5180 没有返回有效 SPI 数据。优先检查 MISO、CS、SPI bus 名称、供电和 GND；在这个问题解决前，读 NTAG215 一定不会成功。

## 标签内容格式

推荐标签中写入 JSON，例如：

```json
{
  "spool_id": "12345"
}
```

也可以是普通文本：

```text
spool_id=12345
```

插件会优先按 JSON 解析，失败后再使用文本正则提取。

## Web 页面调试状态

插件实现了 Klipper `get_status()`，Moonraker/Web 前端可以读取 `[pn5180 mmu_reader]` 对象状态。常用字段：

| 字段 | 含义 |
| --- | --- |
| `reading` | 后台 `READ=1` 是否正在运行 |
| `debug_log` | 是否每次扫描都输出调试信息 |
| `scan_count` | 已执行扫描次数 |
| `last_scan_result` | 上次扫描结果，例如 `no_tag`、`tag_detected`、`spool_applied`、`error` |
| `last_scan_message` | 上次扫描说明 |
| `last_uid` | 上次读到的 UID |
| `last_spool_id` | 上次成功解析/派发的 spool ID |
| `last_error` | 上次错误 |
| `waiting_for_removal` | 是否正在等待已处理标签移除 |
| `recent_events` | 最近关键事件列表 |

后台轮询不会每次无卡都刷屏，只会更新状态；检测到标签、读取失败、spool ID 派发等关键事件会写入日志或 G-code 输出。

## 调试建议

1. 先执行 `PN5180 NAME=mmu_reader DIAG=1`，确认寄存器不是全 `0xFFFFFFFF`。
2. 再执行 `PN5180 NAME=mmu_reader INIT=1`，确认能读到 firmware。
3. 然后执行 `PN5180 NAME=mmu_reader SCAN=1`，把标签靠近 PN5180。
4. 如果隔夜或长时间放置后不读卡，先执行 `PN5180 NAME=mmu_reader RECOVER=1`，再执行 `SCAN=1`。
5. 如果日志中 UID 经常是 `FF FF FF FF` 或 `00 00 00 00`，这通常是假读数，优先检查 SPI 通信。
6. 如果能读 UID 但读数据失败，先把标签保持稳定不要移动，再增加 `rf_timeout` 到 `0.1`。
7. 如果初始化偶发失败，优先确认 RST 是否稳定为 3.3V；更推荐接 GPIO 并配置 `reset_pin`。
8. 如果没有 MCU 控制 RST，PN5180 异常卡死时可能需要重启 MMU MCU 或断电重上电。

## 第一版推荐策略

建议在换料/装料前启动读取，读取到标签后停止或等待标签移除。插件会记住上一张已经处理的 UID，同一张标签未移除时不会重复派发 spool ID。
